# EXECUTION-FLOW — tt-focus-group 워크플로 런 (2026-08-02)

교육용 전 과정 기록 + **메인 세션의 분석**. 팀 런(2026-08-02-bakery-last-day)과 같은
저장소 형식이지만, 실행 주체가 리드의 판단이 아니라 `.claude/workflows/tt-focus-group.js`
코드라는 점이 근본 차이다. 모든 "실행됨"은 워크플로 결과·journal에서 관찰된 사실이며,
참가자 발화·집계는 전부 SIMULATED다.

## 1. 무엇을 실행했나

`Workflow(name: "tt-focus-group", args: {stimulus: "동네 빵집 구독제…", ...})` —
TinyWorld 포커스 그룹의 재현: 캐스트 생성 → 페르소나별 턴 시뮬레이션(3인 × 3단계) →
구조화 추출. 결과: 구독 찬성 1(오미숙) / 조건부 1(한지우) / 반대 1(강병철),
합의 4건·이견 3건 추출 (`03-results.md`).

## 3. 🔴 발견된 결함 — args 문자열화 (이 런의 최대 교훈)

**증상**: 단계 1 진행자 자극과 월드 헤더에 stimulus 문장이 아니라 **args JSON 전체**가
들어갔다 (`02-trace.md` 상단에서 확인 가능).

**원인**: Workflow 호출 시 args가 런타임에서 JSON **문자열**로 전달됐고, 스크립트의
입력 정규화 `typeof args === 'string' ? { stimulus: args } : args`가 그 문자열 전체를
stimulus로 삼았다. 그 결과 audience/objective/fields 인자는 **전부 기본값으로 대체**됐다.

**그런데 실행은 의미적으로 복구됐다**: 페르소나 배우들이 오염된 프롬프트 안의 JSON에서
자극 문장을 스스로 읽어 정상적으로 토론했고, 추출 에이전트는 기본 필드(final_position)
**와** JSON 속에 보인 요청 필드(would_subscribe/conditions/justification)를 모두 채웠다.
**LLM 에이전트의 견고함이 파이프라인의 입력 결함을 가렸다** — 결과만 보면 성공이지만
과정을 보면 설정 절반이 무시된 런이다. "딱 결과만 가지고는 모른다"는 이 기록의 존재
이유를 워크플로 스스로 증명한 셈이다.

**조치**: 두 워크플로(tt-focus-group.js, tt-writing-room.js)의 입력 정규화에
"문자열이 JSON이면 파싱" 방어를 추가했다 (본 런 직후 반영 — 아래 §6).

## 4. 팀 런과의 실측 비교 (같은 저장소의 두 방식)

| | 팀 런 (bakery-last-day) | 워크플로 런 (본 런) |
|---|---|---|
| 사람(리드) 개입 | 재정 8건, 메시지 40여 회 | **0회** (호출 → 완료 통보) |
| 소요 | 수십 분 (왕복 포함) | 9분 10초 |
| 오류 대응 | 워커가 발견 → 리드 재정 → 문서 패치 | **없음** — 결함이 그대로 통과, 사후 분석에서 발견 |
| 품질 관리 | 검증 기준 선고정 + 상호 감사 + 판정 번복 | schema 강제 + 프롬프트에 박힌 규칙(SIMULATED 표기, 트레이스 근거 추출)만 |
| 창발 | 촉발 계단 복원 같은 **설계 개선** 발생 | 설계는 고정 — 창발은 페르소나 발화 안에서만 (기부 순환 아이디어, 3개월 약정 절충) |
| 산출 형식 | 자유 텍스트 (리드가 해석) | JSON (즉시 집계 가능) |
| 재실행 | 사실상 불가 (경로 의존) | `resumeFromRunId`로 캐시 재생, args만 바꿔 반복 가능 |

**요약**: 워크플로는 "검증된 절차의 반복"에, 팀은 "절차 자체를 만들고 고치는 일"에
맞다. 이번 런이 보여주듯 워크플로의 결함은 실행 중 아무도 잡아주지 않는다 — 그래서
워크플로에 넣을 절차는 팀 런으로 먼저 검증하고, 워크플로 런의 기록을 다시 코드
개선으로 되먹이는 순환이 필요하다.

## 5. 00-run-config의 질문 3개에 대한 답

1. **리드 재정의 부재가 어디서 티가 나는가** — 입력 결함(§3)에서. 팀 런이었다면 첫
   워커가 "브리프에 JSON이 통째로 들어와 있다"고 보고했을 것이다. 워크플로에서는
   cast 에이전트가 오염된 브리프를 그대로 받아 최선을 다해 해석했고, 아무도 되묻지
   않았다.
2. **tiny-person-actor는 프로토콜을 지켰는가** — 지켰다. 9턴 전부 THINK → TALK →
   DONE 순서, 시트 우선(강병철의 퉁명한 시장 어투, 오미숙의 맞장구 후 반전, 한지우의
   두괄식·수치 인용이 턴마다 유지), 받은 자극에만 반응(직전 턴 발화를 정확히 인용해
   반박). 특히 단계 2에서 서로의 논거를 수용·수정하는 상호작용(강병철이 한지우의 월
   결제안을 "그건 맞는 말이네"로 인정하며 반론 제기)은 TinyTroupe가 노리는 창발적
   토론의 재현으로 볼 만하다.
3. **팀의 품질 관리가 무엇으로 대체됐는가** — ① schema 강제(캐스트·턴·추출이 전부
   구조화 반환, 빈 반환 0) ② 프롬프트에 박힌 규칙(SIMULATED 라벨, "트레이스 밖 추론
   금지, 근거 없으면 null") ③ 순차 루프가 보장하는 발화 순서. 대체되지 **못한** 것:
   입력 검증, 중간 산출물에 대한 이의 제기, 판정 번복.

## 6. 교훈 → 조치

- **[코드 반영됨]** args 문자열화 방어: 입력 정규화에 JSON.parse 시도 추가
  (tt-focus-group.js / tt-writing-room.js 공통).
- **[코드 반영됨]** 자극 노출 정리: 월드 헤더·1단계 자극에 stimulus만 들어가도록
  보증되는 것은 위 방어의 부수 효과다.
- **[관찰]** 트레이스 누적 비용: 페르소나 4~5인·다단계 런은 턴 프롬프트에 전체
  트레이스 대신 "직전 단계 요약 + 현재 단계 전문"을 넣는 최적화 여지가 있다 — 단,
  TinyTroupe 충실도(전체 지각)와의 트레이드오프이므로 다음 실험 주제로 남긴다.
- **[프로세스]** 워크플로 런에도 이 형식의 기록(설정 → 산출물 → 분석)을 표준으로:
  결과 JSON만으로는 §3 같은 결함이 보이지 않는다.
