오픈소스의 방법을 AI 팀의 작업 규율로 바꾼다

이 저장소의 목표는 에이전트 이름을 많이 만드는 것이 아니다. TinyTroupe가 사람을 페르소나, 환경, 자극, 턴, 추출, 검증으로 다루는 방식을 소스에서 찾아 스킬로 고정하고, 역할이 다른 Claude 워커에게 나눈 뒤, 실제 산출물과 실패 기록으로 다시 검사하는 것이다.

FOR STUDENTS

AI 팀은 정답 기계가 아니라, 큰 문제를 검증 가능한 작업으로 분해하는 도구다

관심 있는 오픈소스를 고르고, 그 프로젝트의 핵심 방법을 찾고, 각 방법을 스킬과 역할로 나누고, 실행 흔적을 남긴다. 결과가 그럴듯해도 과정이 틀릴 수 있으므로 실패와 미검증 항목까지 공개한다. 이 순환을 자기 분야에 이식하는 것이 이 실험의 교육 목표다.

01

문제와 저장소를 고른다

“글을 잘 써 줘”가 아니라 페르소나 일관성, 상호작용, 독자 반응처럼 분리 가능한 문제를 고른다.

02

소스에서 불변 규칙을 찾는다

TinyPerson, TinyWorld, ResultsExtractor, TinyStory, validator가 근거다.

03

스킬로 방법을 고정한다

페르소나·시뮬레이션·추출·스토리·라이팅룸의 입력, 절차, 출력, 금지를 문서 계약으로 만든다.

04

역할마다 산출물을 맡긴다

캐스트, 씬 플랜, 초안, 독자 반응, 편집 노트를 서로 다른 워커가 맡아 한 사람이 자기 답을 채점하지 않게 한다.

05

런과 실패를 함께 저장한다

최종본만 남기지 않고 브리프, 중간 판본, 메시지 재정, 검증표, 실행 흐름을 같은 런 디렉터리에 둔다.

06

현실 검증으로 넘긴다

시뮬레이션 독자는 실제 독자가 아니다. 출판 전 사실 확인과 인간 독자 테스트가 다음 단계다.

FAILURE AS EVIDENCE

그럴듯한 결과가 입력 결함을 가렸다

런타임이 args 객체를 JSON 문자열로 넘겨 자극 문장 대신 전체 JSON이 프롬프트에 들어갔다. 에이전트가 의미를 복구해 결과만 보면 성공처럼 보였다. 과정 기록이 없었다면 발견하지 못했을 결함이다.

교훈: 워크플로 성공은 “파일이 나왔다”가 아니라 입력, 중간 상태, 출력 계약이 모두 맞았다는 뜻이어야 한다.

TEAM OR WORKFLOW?

무엇을 팀으로 풀고, 언제 코드로 고정할까

팀 런

문제와 절차가 아직 흔들릴 때 쓴다. 워커가 이의를 제기하고 리드가 판정을 바꾸며 방법 자체를 고친다.

워크플로 런

입력·출력·실패 조건이 검증된 뒤 반복할 때 쓴다. 빠르고 재실행 가능하지만 중간 판단자가 없다.

올바른 순서

팀으로 절차를 발견하고 검증한 뒤 워크플로로 고정한다. 워크플로의 실패는 다시 스킬과 코드 개선으로 되돌린다.

EVIDENCE BOUNDARY

이 페이지가 주장하지 않는 것

실제 TinyTroupe Python 실행이 아니다. 소스의 방법을 Claude 스킬과 서브에이전트 프로토콜로 재현한 별도 실행층이다.

시뮬레이션 독자는 실제 인간이 아니다. 완독 의사, 선호, 합의 수치는 탐색용이며 시장 조사나 통계가 아니다.

품질 점수는 팀 내부 평가다. 출판 품질을 보증하지 않으며 제빵·세무 같은 사실 항목은 별도 검증이 필요하다.

현실 행동과의 일치가 검증되지 않았다. 중요한 판단에 쓰려면 TinyTroupe가 제공하는 empirical validator처럼 실제 인간 데이터와 비교해야 한다.
